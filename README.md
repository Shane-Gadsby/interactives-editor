# interactives-editor

The browser editor for Interactives. You use it to build interactive 2D experiences:
- artboards with vector shapes, pen paths, text and images;
- real web controls: buttons, inputs, links, HTML/iframe embeds and video;
- keyframe timelines;
- a node-based interaction graph;
- variables and data bindings;
- custom JavaScript;
- step-through explainers: a timeline's markers become steps (Next plays to the next marker, Back plays back, dots, a generated step bar, scroll to scrub);
- responsive artboard sets: variants of an artboard shown by the page's width (Responsive section of the artboard, Add narrow/wide variant, breakpoints, a pairing report of what would not carry), listed under their base in Layers, with pills on the canvas and a Page width slider with breakpoint marks in Preview. The runtime side is the player's `variants.ts`.
- sticky notes: the Note tool (`S`) leaves author-only notes on the canvas (`src/canvas/NotesLayer.tsx`, edits in `src/lib/notes.ts`, markdown-light in `src/lib/note-text.ts`). They live in the document (`artboard.notes[]`, and `project.notes[]` for canvas-level ones; the format and `stripNotes` are the player's `notes.ts`), so they undo, save and go live like any edit, but they are not layers. Single HTML, share, embed, review and the pictures never carry them: `standaloneHtml` strips them, and `shared/notes.mjs` strips them again on the server (share PUT, review GET). The project JSON and .ixp keep them. The eye button beside the tool is the `showNotes` preference. MCP: `list_notes`, `add_note`, `edit_note`, `remove_note` and the `add_note`/`set_note`/`delete_note` edit ops. Starters call `addNote(artboard, {x, y, text, anchor?})` from `src/lib/branded/kit.ts`.
- Fill in this starter: a plain form for a starter's content (the Fill in tab beside the Checklist, `src/panels/ContentFormPanel.tsx`). A starter declares its fields in its set's `forms.ts` (`src/lib/branded/sets/<set>/forms.ts`, written with the `FormKit` in `src/lib/branded/form-kit.ts`: a variable by name, a layer by page and layer name, a question by its layer, `covers` for the checklist items a field answers). `projectFromBrandedStarter` resolves the names to ids and stores the result as plain JSON in the document (`Project.contentForm`, the types and `cleanContentForm` are the player's `content-form.ts`), so it survives renaming and goes with Save as template. Every field is bound to ordinary data (a variable's starting value, a layer's text, a question's settings through `setQuestionSettings`, a graph node's parameter, a picture slot, a project setting) and `src/lib/content-form.ts` reads and writes it inside `EditorStore.update`, so edits undo, save and go live like any other, and the Variables, Layers and Question views show them. List fields have rows from a list variable, from a question's options, blanks, pairs, groups, cards or extras, from a JSON parameter, or fixed rows made of separate bindings. A checklist item names its field (`TemplateChecklistItem.field`) and the checklist shows a Fill in button for it. `test/content-form.test.ts` fails when a starter has no form, a binding points at nothing, a checklist item about content has no field (items to check or try, and ones listed under the form's `elsewhere`, are exempt), or a field does not round-trip through the store and undo.
- graph notes: the same notes on an artboard's interaction graph (`artboard.logic.notes[]`, graph coordinates, `anchor.layerId` a node or group id with `lx, ly` the offset from its corner). Drawn by `src/panels/GraphNoteNode.tsx` as React Flow nodes, edited through `src/lib/graph-notes.ts` (pure parts in `graph-notes-core.ts`), added from the graph's note button and the right-click menus. `tidyGraph` (`src/lib/graph-tidy.ts`) takes the notes: anchored ones give their node room and move with it, loose ones are moved off whatever they landed on. Copying a node copies its notes (`logic-clipboard.ts`). `stripNotes` (player and `shared/notes.mjs`) drops them everywhere players are sent a project, and the eye button and its count cover them. MCP: `add_graph_note` / the `add_graph_note` op, and `list_notes`, `edit_note` (`anchor_id`), `remove_note` for both kinds. Starters call `graphNote(artboard, {text, anchor: node-or-group})` from `src/lib/branded/graph-kit.ts`; `test/starter-graph-notes.test.ts` keeps the list of starters still to annotate.
- Interactions palette (`src/panels/GraphPalette.tsx`): a search box that ranks with the properties panel's scorer (`src/lib/node-search.ts`: `NODE_SYNONYMS` beside `PROP_SYNONYMS`, `rankNodes` over `rankEntries` in `prop-search.tsx`; the Add and connect menu goes through the same function), Events/Actions/Logic and topic chips, and a fold per topic (`NODE_GROUPS` in the player's catalog; folds are kept in this browser, `lib/graph-palette.ts`). The artboard picker above it (`ArtboardPicker.tsx`, `lib/artboard-picker.ts`) reads and writes the store's `activeArtboardId` only. `/` or Ctrl+F focuses the search, Alt+Up/Down (or Ctrl+[ ]) steps artboards.
- node descriptions: each catalog node has a `summary` (one sentence, 20 words or fewer: the inspector, palette tooltips and search read it), `details` (the rest: the generated node reference and the MCP's node list carry it, after the summary) and `gives` (the `event.*` names an event makes available). `description` is still there as summary plus details.
- branded starters (`src/lib/branded/`): `kit.ts` builds the pages (`brandedPage` makes one page master per kind and size for the chrome, locked, so a page holds only its title and footer and masters sit after the pages in the artboard list), `graph-kit.ts` is the one set of graph builders (`addVar`, `Graph`, `graph`, `Flow`, `seq`, the action tuples) with `finishGraphs` (the graph tidy on every artboard) and `parts.ts` the native pieces (`progressBar`, `pageNav`, `dialogPanel`, `keyNavList`, `stack`/`fill` auto layout). `projectFromBrandedStarter` runs the graph tidy, `settleLayout` and the artboard tidy. `layout-check.ts` is the automated layout check (`test/starter-layout.test.ts`: a button over words, anything in the logo's clear space, words off the page or into the accent bar; `STARTER_LAYOUT_REPORT=<file>` writes the list, `STARTER_LAYOUT_STRICT=1` fails on it; a starter can give `layoutStates` to be checked in states other than its first; `overlay(layer)` marks an intentional overlap).
- run highlights: Preview's **Beside editor** button moves it up to the right so the canvas and the Interactions graph show while it runs. The player's `flow` event (`{k:'node'|'edge'|'hit', ...}`, batched into `interactives-debug` messages; off in exports) goes through `src/lib/run-flow.ts`: nodes that ran light green (`ran`), an event whose Only if said no goes grey (`held back`), followed wires pulse (`LogicGraph.tsx`), the clicked layer gets a ring on the canvas (`canvas/HitPulse.tsx`), and the events list says why a click did nothing and selects a line's node. Editor-only, never saved.
- interactions room: `src/lib/interactions-room.ts` lifts the bottom panel from its default 260px to 440px while the Interactions tab is open and puts it back after; a panel the author sized is left alone, and a height set while the graph is open is remembered (localStorage `ix-interactions-room`).
- graph reveal: `src/lib/graph-reveal.ts`. After the person adds nodes from outside the graph (the behaviour dialog, an empty event from the Inspector or the canvas menu, a timeline marker's "When the playhead reaches this"), `revealAdded` opens the Interactions tab on the graph, picks the new nodes, marks the graph as the key area and asks `LogicGraph` to frame them (`frameRects`: padded, never past 100%), focus the event and glow them (not with reduced motion). It is called only by those local actions, so undo, redo, live edits from others and agents never move the view. Per-person pref `showNewInteractions` (on by default; server `PREF_KEYS` carries it) turns it off, and each caller's `quiet` is then the old behaviour. `applyBehaviour` returns the ids it wrote.
- no-code interactions: `src/lib/flow-describe.ts` is the one flow description (a graph as plain sentences, from small templates and the catalog's labels, summaries and settings; `buildFlow`, `flowSentence`, `flowLines`, `flowsForLayer`, `removableWithEvent`, turning a flow off by putting `false &&` in front of its Only if). It is read only, so it feeds the Inspector's Interactions rows, the graph's "Read as sentences" view (`panels/FlowSentences.tsx`, store `logicView`) and a behaviour's preview. `src/lib/recipes.ts` are the one-click behaviours ("When clicked: go to the next page / show a layer / play a sound / add 1 to a counter..."): `buildBehaviour` is pure and writes an On pointer + one action through `lib/click-flow.ts` (plus a new variable, plus a layer set to start hidden), `applyBehaviour` writes it in one `update`. `components/BehaviourDialog.tsx` is the chooser (`openBehaviours`, mounted in `App.tsx`). `src/lib/condition.ts` parses the plain subset of a yes/no formula (comparisons, &&, ||, !, `.includes`, `.length == 0`) into rows and back and returns null for anything else; `components/ConditionField.tsx` is the picker UI used for Only if, If's condition, a timer's Only while and a yes/no binding's formula. `src/lib/expr-check.ts` is the line under every `ExprField` (what it works out to, or what is wrong in words, with a did-you-mean fix).
- go to page: `canvas/PageLinkLayer.tsx` draws a round handle on the selected layer (drag it onto a page, or click for a list) and faint arrows between pages for every route (`lib/page-link.ts` `pageRoutes`; switch off from the canvas menu, `lib/page-routes-pref.ts`). The Inspector's **Go to page** section (`panels/PageLinkSection.tsx`) does the same from a list. It writes an On pointer click and a Go to artboard node through `lib/click-flow.ts` (`writeFlow`, `writeClickFlow`, `appendStep`: the one small "write these nodes for a click" helper), and never rewrites a click with an Only if.
- page navigation: `lib/page-nav.ts` generates Back, Next, the page number, dots or a progress bar along the bottom of the page (the same wiring and names as `branded/parts.ts` `pageNav`: Go to artboard next/previous, `pageNumber`/`pageCount`), tagged `page-nav` so adding again swaps the style. The Inspector's **Page navigation** section (`panels/PageNavSection.tsx`, also for several selected artboards).
- page masters: an artboard holds the layers every page shares (logo, accent bar, footer) and pages draw it under their own (`Artboard.master`, the player's `master.ts`). The Page master section of the artboard (pick a master, leave layers off by name, fill `{slot}` text, Edit master, Detach; on a master: the pages using it and which layers go over), a gold `master` badge in the Layers list, and Make this a master / Edit master / Use as master for… in the artboard's context menu. Master layers are read-only on a page, drawn by the canvas, pictures, stills, thumbnails and exports (a Lottie flattens it), carried into library components and held by the brand lock. `src/lib/page-master.ts` has the actions and `extractMaster(project, layerNames)`, which turns chrome repeated on pages into masters (for the template sweep). The MCP `set_artboard` takes `master`, `masterHide`, `masterSlots`, `masterOver`.
- one grid for the Properties panel, the graph's node settings and the Keyframe column: nine tracks (label, control, unit, key, chain, label, control, unit, key), declared once in the "field rows" block of `src/styles.css` (`--cols`; the widths are `--label-w`, `--label-w-2`, `--field-trail`, `--field-key`, `--field-chain`, `--field-gap`). A single field spans it with its label in the first track and its box ending at the same right edge as the second box of a pair; a pair (X and Y, W and H) puts its second label in the same track in every row; a tick box starts under the controls; a row of buttons is equal cells from the left edge; every control is `--field-h` high, lines are `--row-gap` apart and a sub-heading starts `--group-gap` above. Below the `panel` container width (316px) pairs go one field per line, and a dropdown, text box or px/percent box is always a line of its own. Fields are `fieldClass()` components (`src/components/ui.tsx`) with no widths of their own; `test/field-layout.test.tsx` holds the contract.
- the pictures and videos in `public/help/` are shot in the light theme (Preferences > General > Theme: Light), headless Chrome, sample projects only, videos H.264 (yuv420p, no audio, 1280 wide). `scripts/check-help-images.mjs` (and `test/help-images-light.test.ts`, which runs it) fails on a picture whose editor is dark; a picture that is dark on purpose goes on the `ALLOW` list in that script with the reason. The same check for the Toolbox docs is `si-manager/scripts/check-doc-images-light.js`.
- the Help button follows what is highlighted: `src/help/context.ts` is the one table from layer type, tool, graph node, Properties field and panel to a help topic and anchor, `currentHelpTarget` in `src/components/Dock.tsx` gathers the selection, tool and focus, and `test/help-context.test.ts` fails when a layer type, tool, node kind, panel or inspector Section has no real topic behind it. F1 and ? do the same as the button; the drawer keeps its own back and forward history (`src/help/history.ts`). Everything that floats shares the `--z-*` scale at the top of `src/styles.css` (Preview sits above the help drawer, so help asked for while it is open goes to a new window, `src/lib/overlays.ts`), and `test/overlay-order.test.tsx` checks the order. The inspector remembers folded sections per section key (`src/lib/section-fold.ts`): a `<Section>` needs a plain-text title or an `id`. For a signed in person the folds are the `sectionFolds` preference (so they follow them between machines; the old `ix-section-folds` localStorage value is merged in once, then cleared); guests, and folds made before the server's preferences arrive, use localStorage.
- selecting several artboards and artboard groups: Ctrl/Cmd+click or Shift+click on an artboard's name on the canvas, or Ctrl+click and Shift+click on its row in Layers, selects several (`artboardPicked` in the store, read through `pickedArtboardIds` in `src/lib/artboard-groups.ts`); dragging a name moves them all, Delete asks and removes them in one step, and the Inspector shows align, distribute, group, tidy, duplicate and delete for the set (`src/panels/ArtboardsSelection.tsx`). A group is a name in `project.artboardGroups` plus `artboard.group` (both optional, kept clean by the player's `sanitize.ts`): Layers lists it as a foldable folder row, the canvas draws a dashed frame round its artboards (derived, not stored), and Tidy up keeps each group together as a block (`src/lib/artboard-tidy.ts`). The menus and prompts are in `src/lib/artboard-commands.ts`.
- styled text edited like a word processor: while a text layer is being edited, a floating toolbar (`src/canvas/TextToolbar.tsx`, logic in `src/lib/text-toolbar.ts`) gives bold, italic, underline, strikethrough, colour, size, font, link and clear formatting for the selected characters, with Ctrl/Cmd+B/I/U/K, Shift+X and \\. Storage stays as runs; the Inspector keeps the runs list under Advanced.
- script layers: a box painted by a script every frame (generative art, charts), with starter templates.
- a public interface for developers who embed a project (Public interface tab: variables as inputs and outputs, messages sent and received, with descriptions; a generated reference page and TypeScript definitions; export warns when the list has drifted; an option to take only public inputs from outside). The player side is in `interactives-player/src/interface.ts`; the list is edited by `src/lib/public-interface.ts` and `src/panels/InterfacePanel.tsx`.
- an optional attributions and references list (Attributions tab: entries with kind, title, creator, source link, free-text licence, year and private notes, linked to assets so the Assets panel can show which files have no attribution yet). It lives in the project as `attributions`, with `settings.credits` choosing whether the player shows a Credits button and whether exported and shared pages carry the list (`withPublishedCredits`, notes never leave). The player side is `interactives-player/src/attributions.ts` and `credits-ui.ts`; the list is edited by `src/lib/attributions.ts` and `src/panels/CreditsPanel.tsx`.
- the editor's own colours (`src/styles.css`, the first `:root`): the palette's greys and gold, and nothing blue for anything chosen. Every keyboard focus ring is `outline: var(--focus-outline)` (gold, with `--focus-halo` or `--focus-inset` for the thin dark edge that keeps it at 3:1 on white), a chosen thing without a fill of its own uses `--sel-ring`, a gold fill carries `--primary-fg` text, a bar or curve on a panel is `--key-on`, and links are `--link` (dark text underlined on the light theme, gold on the dark). `--accent` and `--accent-2` no longer exist. `--info` (and `--action`, which is it) is the one deliberate blue, for what a kind is (an Action node, a review dot) and never for what is chosen. `test/no-old-blue.test.ts` fails on the old tokens, on any other blue written out, on a focus rule that draws its own outline and on contrast of the ring and links.
- themes and colour tokens (Themes tab, `src/panels/ThemesPanel.tsx`, `src/lib/themes.ts`): a project's `themes` list holds colour tokens with a value per theme (Light, Dark, High contrast); a fill, stroke or text colour that says `token:<id>` follows one. A Tokens tab in the colour picker (`src/components/TokenPicker.tsx`) links a colour to a token (the swatch shows a ring, a named chip replaces the hex box, the x detaches), a theme switcher in the top bar and in Preview (with a simulated viewer and a simulated Moodle host), colour styles convert to tokens, imported files keep plain colours, and the accessibility checker checks text contrast in every theme and warns about a token colour on a fixed colour. The starter tokens are the StudyDesk toolbox look, taken from the shared palette (`/styles/palette.min.css`, si-studydesk-styles) and never written down as colours: the player's `starter-look.ts` names the palette property the toolbox uses for each role, the colours come from the live file with a generated snapshot as the fallback (`interactives-player/scripts/sync-palette.mjs`), and a token made from the palette keeps its palette property per theme (`ThemeToken.palette`). The editor fetches the palette when it starts (`lib/palette-look.ts`), refreshes linked tokens when a project opens, and a hand-edited colour drops its link. A blank New project (`newProjectWithThemes` in `lib/themes.ts`, called from `Home.tsx`) starts with the starter themes and linked tokens and the artboard on `color/background`; projects made before that and imported ones start with none. Light is the toolbox as it draws itself, so these pairs are below WCAG AA (the Themes panel and the accessibility checker report them as they are; this is the shared palette, not a bug): muted text on background 2.59:1, muted text on surface 2.38:1, muted text on muted surface 1.96:1, primary on background 1.75:1, link on background 3.60:1, link on surface 3.30:1, outline against background 2.59:1, outline against surface 2.38:1, focus ring on background 1.75:1, focus ring on surface 1.61:1, success on its surface 3.90:1, error on its surface 3.13:1, warning on its surface 2.67:1. Dark and High contrast pass every pair. New layers (`lookDefaults`), the question kit, the step bar and the built-in starters take those colours by token name when the project has the tokens (`lookFor`) and plain Light values when it does not; a project from before the look keeps its stored values until "Update starter colours" (`upgradeStarterTokens`) is pressed. The runtime side is the player's `themes.ts`.
- shader layers: a box painted by a GPU fragment shader (WebGL) with animatable, bindable uniforms, a library of starter presets, and a shader filter for image layers.
- progress bars (a track and a bar filling to a bindable, animatable value, with a progressbar or meter role) and charts (column, bar, line, pie and donut from a data expression, with a data preview in the inspector, theme token colours, a keyboard-readable readout and a hidden table for screen readers); the Data group of the tool bar. Panels in `src/panels/DataLayerInspectors.tsx`.
- connectors: a line or arrow joining two layers that follows them (straight, elbow or curved, with arrow or dot ends, a label, and one per item of a list when its ends pick copies of repeated layers). The **Connector** tool (K, in the Draw group) drags from one layer to another with ends snapping to the layers' sides, a selected connector has a handle on each end, and the inspector's Connector section is in `src/panels/ConnectorInspector.tsx`; what the tool works out (the layer under the pointer, side snapping, repeater templates) is in `src/canvas/connect.ts`. The routing is the player's (`interactives-player/src/connector.ts`); the canvas records each connector's route as drawn (`recordDrawnGeometry`) so its outline and picking follow the line.
- the **Mind map** and **Flowchart** branded starters (Explore and reveal, `src/lib/branded/sets/explore/mindmap.ts` and `flowchart.ts`) are built on connectors and the player's diagram layouts (`mindMap`, `flowChart`, in `interactives-player/src/diagram.ts`): the boxes and the lines are repeaters over a layout list, so the author edits data. Mind map: explore (fold, details dialog, arrow keys, outline view) and build your own (edit, drag to move; the author's `keepMap` variable keeps the learner's map for next time or not, with Save, Start a new map after asking, Open a saved map from a downloaded copy pasted in, and downloads as a text outline, a picture page or a copy). The Flowchart has no learner-made content to keep. Flowchart: follow (answer each decision, the route lights up, a text version) and complete (a matching question with blank shapes). Tests are in `test/branded-diagrams.test.ts`.

Projects are stored on the server in MongoDB. They export as a single self-contained HTML file or as a `.ixp` package (zip), and import back from `.ixp`.

The runtime lives in the sibling repo [interactives-player](https://github.com/Shane-Gadsby/interactives-player). The editor draws its canvas with that player's renderer, and its exports embed that player.

## What's in 0.5

Interactives 0.5 is the first beta. A short tour of what is in it, newest ideas first; every item has a page in the in-app help (F1), and the Welcome page has a **Getting started as a beta tester** section with what to try first, how to report a problem and the known limits.

**Working together**
- **Share and Export are separate.** Export only makes files (single HTML, package, JSON, Lottie, PNG, SVG, the public interface reference). Share holds the links and people: **Share link** (plus the **Link for StudyDesk**), **Invite to collaborate**, **Save as template** and **Share for review**.
- **Collaborators**, invited by name, email or username (`/api/people` looks them up in the suite's `user-lookup`, staff only), edit live with the owner.
- **Review comments**: pins that follow their layer, replies, resolve, assign, @mention, in-app notices, a review link with its own page (opening it takes a sign in), kept apart from the project so they are never exported.
- **Templates, examples and remix**: Save as template with a checklist of what to change, a Templates tab (Mine, Shared, Built-in, Examples; the Built-in one with a search box, goal chips and Play on every starter), a Checklist tab in projects made from one, Update from template, **Allow remix** on a share link, and read-only examples shipped in `examples/` (now including a bones rig, a matching question and a hotspot question).
- **Libraries** of components and styles, and **live editing** with revision history.
- **Start a new project** asks how: blank (with the Light, Dark and High contrast themes), a copy of one of your projects or templates, a built-in template, or a copy of an example.

**Learners**
- The **learner page** (`/play/:token`, the Link for StudyDesk) remembers progress, reports score and completion, and passes on what learners do.
- **Embed code** (Share link dialog, `src/lib/embed.ts`): the Link for StudyDesk wrapped in the iframe the Toolbox writes for its own items (`toolboxItems.js`: `title`, `?title=&cdtID=` in the src, `data-cdt-id`, `allowfullscreen`, `width:100%` and an `aspect-ratio` from the start artboard), with `allow="autoplay; fullscreen"` plus `microphone` / `camera` when the share record's `sensors` declare them. One code serves StudyDesk, StaffDesk and the open site (same ILAR host, same si-manager script); the host is whatever the editor is served from. The learner page relays the player's height message to its parent with `setILARSize`, since the player's own message comes from two frames down and si-manager can't match it to an iframe.
- **Course and learner context**: a built-in, read-only `context` data source (course label, code, name, term, year, the learner's first and display name, signed in / student / staff) in expressions, text, the graph and `ix.context`, with editable sample values in the Data panel for the canvas and Preview, and a **Per-course values** table (course label pattern to variable values) applied at start on the Link for StudyDesk page. The learner page answers the player's `context` postMessage from `fetchActivity` (`contextFrom` in `shared/records.mjs`: never the username, email or id, never sent to analytics). The project fields are `courseValues` and `sampleContext`; the logic is the player's `context.ts`.
- **Results and progress**, **Insights** (artboards reached, a click heat map on the canvas, steps, answers per question, your own records) and **Learner records** switches.

**Questions and interactivity**
- The **question kit**: multiple choice and response, true/false, fill in the blank, ordering, **matching** and **hotspot**, with hints, tries, scoring, shuffle and banks, and import from a GIFT file. Drag and drop, step-through explainers, narration and captions, a public interface for hosts, scripts, script layers and shader layers.
- **Accessibility**: layer roles and keyboard operation, and a checker with a sign-off report.

**Design and layout**
- **Themes and colour tokens** (Light, Dark, High contrast). The starter look is the toolbox's, read live from the shared StudyDesk palette (`/styles/palette.min.css`) so it stays in step, with the pairs that fall below AA listed in the help. A **font picker** searches every Google font (Open Sans by default) in the Inspector, the text toolbar, the project Fonts and Preferences. Also colour presets from the toolbox palette, several fills and strokes per shape, paint order, per-corner radius.
- **Auto layout** with grids, stacks, a layout item section, line gap, **percent padding, margin and gap**, and hidden layers that take no space.
- **See-through layers are not clickable** by default while playing (a faded layer lets clicks through), with a per-layer **Clickable while see-through**; paths, polygons and stars take clicks only where painted.
- **Layers hanging outside a clipping artboard** show as a faint, diagonally striped copy beside it on the canvas (a preference), so they can still be found and picked.
- The editor itself: **tool groups** that fold (Shapes and Draw open, Media, Web and Rig folded), a 320 px Inspector, resizable panels, a **timeline settings** gear, a floating text toolbar, themed dialogs everywhere.

**Motion**
- Timelines with markers, frame snapping, blends and transitions, joysticks, text modifiers, shape morphing and the Bend tool, and **bones and IK** with a **Build an example to try** button.

**Import and export**
- Rive **.riv** (state machines, view models, layouts, joysticks, masks, scroll, lists, bones) and the Rive editor's **.rev**, Lottie and dotLottie, Photoshop, Illustrator, PDF, AutoCAD DXF, VectorCraft, PhotoCraft and SVG, with linked design files that update when the file does.

**Under the hood**
- The editor records how it is used and where it breaks (mandatory, scrubbed, written down in the help topic *What the editor records*), and published projects report how they ran. The **version** (`Version <release> · build <editor commit>.<player commit>`, from `src/lib/version.ts` and `vite.config.ts`) sits behind a small (i) icon (hover to read it, click to copy it) beside Help on the help and projects pages, in the help drawer, in the F1 quick search and in the Preferences title bar, so a bug report can name the exact build.
- An MCP server lets an AI agent join a live session and edit alongside people.

**Known limits** are listed in the help (Welcome, *Known limits in 0.5*): results go to the Toolbox's records and not the StudyDesk gradebook yet; themes are colours only; libraries keep only their latest version and carry no scripts; comments have no email; linking design files needs Chrome or Edge; `.dwg` files must be saved as `.dxf`.

## Layout on disk

Like the rest of the StudyDesk Toolbox suite, this app expects sibling checkouts:

```
apps/
  suite-libs/            mongo-connect, cache-headers, session-check, version-reporting, crash-guard
  toolbox/               public/sys/js/powerUser.js (power user rule)
  interactives-player/   only needed to build the frontend
  interactives-editor/   this repo
```

## Run

```bash
npm install
npm run build    # builds ../interactives-player, then the editor into dist/ (committed)
npm start        # node index.js, http://127.0.0.1:3048/interactives/ (behind haproxy: /interactives)
npm run server   # same, under nodemon
npm run dev      # vite dev server with HMR; /api is proxied to the server on 3048
npm test         # vitest (read the summary lines: a red file is a real failure)

```

Before every commit that changes `src/`: `npm run build` (it type-checks, builds the player first, and rebuilds `dist/` and `mcp/dist/`), then `npm test`.

`dist/` is committed on purpose. Test and prod deploy with `git pull` + `npm install` + restart and have no build step. Run `npm run build` before every commit that changes `src/`.

The server makes brotli (quality 11) and gzip copies of every text file in `dist/` over 1 KB itself, in the background after `app.listen` succeeds (`precompressed.js`; set `INTERACTIVES_PRECOMPRESS=0` to turn it off). They live in `storage/_compressed/` (outside git, so nothing compressed is ever committed), with a `manifest.json` of the size and mtime each copy was made from. A restart reuses every copy that still matches and only redoes changed files; copies of files that went away are deleted. It runs one file at a time on the thread pool, biggest first, so the main chunk is ready first and the event loop is never held (about 9 s of one thread for the whole of dist on first boot, 2 ms on a restart). Until a file's copy exists, the plain file is served. When `Accept-Encoding` takes brotli (else gzip) and the copy is current, it is sent ahead of `express.static` with `Content-Encoding`, `Vary: Accept-Encoding` and the same `Cache-Control` as the plain file (the suite's `setHeaders`, called with the plain file's path). A Range request, a picture, a changed file or no match all fall through to the plain file. haproxy's own `compression algo gzip` skips a response that already has a `Content-Encoding`, so nothing is compressed twice. The main chunk goes from 1,991 KB (gzip) to 1,398 KB (brotli) on the wire. `npm run dist:compress` makes the same copies by hand.

The insights route reads the rows back and `insights()` in the same file counts them; anyone can post to the analytics endpoint, so every row is cleaned again when read. The page's CSP allows `script-src 'self'` for `/utilities.js`. The player side is `interactives-player/src/records.ts`; the tab is `panels/InsightsPanel.tsx` (counts and bars, the click heat drawn by `Canvas.tsx` from `store.heat`, CSV from `lib/insights.ts`) and the switches are `panels/RecordsSection.tsx` writing `settings.records`.

Data lives in two places:
- **MongoDB:** database `lti-interactives`.
  - `projects`: `{_id, name, owner, created, updated, rev, meta, doc, docChunks, share?}`, where `doc` is the project JSON stored as a string. A document over 12 MB (UTF-8) doesn't fit beside the rest of a 16 MB record, so it goes into `doc-chunks` instead: `doc` is null and `docChunks` is `{key, parts, length}`. `shared/docstore.mjs` does both ways; read and write a document through it (`store.parse(row)`, `storeProjectDoc`), never `row.doc` directly.
  - `projects-bin`: a deleted project's whole row as it was, plus `binned: {at, by}`. Delete moves the row here and its files to `storage/_bin/<id>/` (`files/` the asset folder, `share.html`, `thumb.jpg`), so no route finds it and its links stop at once; revisions, comments, learner records, doc-chunks and a published library are left in place. Restore moves it all back. `purgeProject` removes everything (what delete used to do at once): from **Delete forever** and from the sweep at start and every 6 hours, for anything binned over 30 days (`binDays`). No index: it is small and listed per owner.
  - `doc-chunks`: `{_id: '<key>:<n>', key, project, n, data}`, the parts of split documents. The key is `p:<project>:<rev>` for a project and `r:<revision id>` for a revision, so a new set never overwrites the one the row points at: the parts go in, the row moves, then the old set is dropped (or the new one, when the row didn't move). Looked up by `_id`, so no index; dropping a project's parts scans this collection, which only holds the rare huge documents. `INTERACTIVES_DOC_INLINE_MAX` and `INTERACTIVES_DOC_PART_CHARS` lower the sizes for tests.
  - `libraries`: `{_id (the project id), name, owner, version, hash, updated, note, brand, shared: {everyone, users[]}, components, internals, styles, history[], snapshot}`. One per published library; `snapshot` is the latest version's JSON string (artboards, variables, fonts, data sources, asset records, styles) and `history` keeps a short list of what each version held. A project's own document gets `library: {version, updated}` when published, and `meta.library` says it is marked as a library.
  - `templates`: `{_id, name, description, owner, created, updated, version, hash, shared: {everyone}, checklist[], source (the project it was saved from), thumb, artboards, preview, history[], snapshot}`. One per saved template; `snapshot` is the project JSON as a string. Files: `storage/_templates/<id>/` (asset files with `<id>.json` sidecars, and `thumb.jpg`). Indexes `owner.username_1` and `shared.everyone_1` in `suite-libs/indexes.js`.
  - `prefs`: `{_id (username, or `guest`), prefs, updated}`: the person's own editor preferences, read and written by `/api/prefs` and kept by the browser too.
  - `revisions`: `{_id, project, created, rev, by, reason, size, doc, docChunks}` (split the same way as projects). A snapshot at most every 5 minutes per project while it is saved (PUT or live room save), plus one before each restore. The newest 100 per project are kept.
- **Asset files:** stored under `storage/<projectId>/<assetId>`, each with a `.json` sidecar. A published library's snapshot assets are copied to `storage/_libraries/<projectId>/` (same layout) so they survive edits to the library project. Share links are `storage/shares/<token>.html` (and `<token>.prev.html`, the page the last update replaced). `INTERACTIVES_STORAGE` moves that folder; on test and prod it is symlinked to the larger storage pool. `storage/` is gitignored. Because a project id is a folder name, `validID` (in `shared/safety.mjs`) refuses `shares`, `thumbs`, `_libraries` and anything starting with `_`. Asset responses (project and library) go through `assetHeaders` in the same file: `nosniff`; images (not svg), video, audio, fonts, JSON, CSV and plain text keep their type; svg gets a CSP that stops scripts; anything else is served as `application/octet-stream` with `Content-Disposition: attachment`.

**Live editing.** Opening a project joins a room held in memory by the server, which holds the document, an op log and the connected clients. Edits are diffed into id-addressed ops (`shared/ops.mjs`, the same file the server uses): set a property, insert after an id, delete an id. The last write wins per property, in the server's order.

- Order in a list is settled on the client, not on the wire: each session keeps a copy of the server's document (every op the server sends, its own included) and, after someone else inserts into or deletes from a list it also has edits waiting in, works out the order the server will end up with (`orderFixes` in `shared/ops.mjs`) and moves its own list to match. The moves are a local-only `mv` op; nothing new goes to the server, so old and new clients and servers mix freely.
- The server saves the room to MongoDB a second after the last op, but never more than 10 seconds after the first unsaved one (`liveSaveMax`), when the room empties, and on SIGINT/SIGTERM. Saves run one at a time per room. A failed save keeps the room dirty, retries by itself (2 s doubling to a minute) and sends the room `stored {ok: false, error}`, then `stored {ok: true}` once it works; `hello` carries the current `stored` too. The editor shows **Save failed** / "Not saved yet" for as long as it lasts, since ops reaching the room is what normally reads as Saved.
- `PUT /api/projects/:id` answers 409 only for a real conflict (rev moved, a racing insert, mongo's write conflict), 413 with a "too big" message for a body over 64 MB or a record mongo won't take, and 500 with the reason for anything else. The editor retries 0/5xx/408/429 by itself (2 s doubling to a minute, and on `online`).
- Clients reconnect with `since=<seq>`, and missed ops are replayed.
- Undo only reverts your own changes, because remote ops are also applied to the undo history.
- A plain PUT (a non-live client or an import) replaces the room and tells everyone to reload.
- Rooms live in one process, so run a single instance per box.

The projects list wants the index `owner.username_1_updated_-1`, and revision history `project_1_created_-1` on `revisions`, both in `suite-libs/indexes.js`. The libraries list (`$or` of owner, shared with everyone, shared with a username) wants `owner.username_1`, `shared.everyone_1` and `shared.users_1` on `libraries`. Everything else is looked up by `_id`.

Access works like this:
- A person sees and changes only their own projects.
- Admins and power users (si-admin's "Power Users", the toolbox's `powerUser.canUse`) see everyone's projects with F9 / Ctrl+F8 on the projects page.
- Until `SUITE_SESSION_ENFORCE=1` is set, refusals are only logged, same as `session-check`.

## Fonts (the Google fonts cache)

Browsers never call Google for a font. `fonts-proxy.js` (mounted at `/interactives/fonts`) fetches a family's stylesheet from Google the first time anyone asks (with a current browser's user agent, so it is woff2), rewrites every font file in it to `file/<sha1 of Google's url>.woff2` on this server and keeps both under `storage/_fonts/{css,files}` (not in git; `INTERACTIVES_FONTS_DIR` moves it). A font file is fetched the first time a browser asks for it (a family's css names a file per script, so nobody downloads the Cyrillic one for English), and everything after that comes off disk: the css `Cache-Control: public, max-age=3600` (the media tier, since Google can change a family), the files `public, max-age=31536000, immutable` (the name is a hash of the versioned Google url). Open Sans, the font of every branded starter, is fetched at start-up (`PREWARM` at the top of the file).

It is not an open proxy. Only families in `src/data/google-fonts.json`, weights as `100` to `900` (at most nine), `text=` only when it is the family's own name (the picker's previews), a file only if its url appeared in a stylesheet this server fetched itself and only from `fonts.gstatic.com`, 400 KB per stylesheet and 2 MB per file, at most 4000 stylesheets and 8000 files kept, and 150 cache misses a minute per address (400 in all). Anything over answers 429 or 503; a cache hit never counts.

A failure is soft everywhere. Google down or refusing answers 502 (remembered for five minutes); the stylesheet keeps Google's own url as a second `src` for every file; and the editor and the player retry a stylesheet that errors from Google's own address, so text still renders. The player takes a `fontsBase` option (the full url of this route) and builds its `<link>` from it; with none it uses Google as before. The editor sets it on previews and on the Single HTML file / share pages only when fonts are not embedded (embedded files carry their fonts and call nothing). The Fonts section of `/suite-docs` should say: where the cache lives, that deleting `storage/_fonts` is safe (it refills), that `INTERACTIVES_FONTS_PROXY=off` switches it off, that the box needs outbound https to `fonts.googleapis.com` and `fonts.gstatic.com` only for the first request of each family, and that learners' browsers never contact Google.

The player also holds its first view back (up to 1.5 s) until the fonts that first artboard uses have loaded, so text is never shown in a fallback face and then jumps, and it loads the other artboards' fonts in the background. The editor canvas does the same on opening (and never makes or keeps an artboard picture before the fonts it uses have loaded).

## The Spelling test voice

A spelling test plays a spoken word, and for a graded test the word can't be in the learner's page, so the browser can't be the one that speaks it. The voice is made **while someone is authoring** instead. In a spelling question's **Voice for the word** section the editor sends the accepted spelling (or the author's *Say it like* respelling, plus an optional sentence) to `POST /api/voice/speak`, gets a wav back, stores it as an ordinary sound asset (`lib/voice.ts`, `panels/VoiceSection.tsx`) and points the word's Play sound node at it. The shared page holds only audio: `Question.voice` (the voice settings, the respelling, the sentence) is dropped by the player's `stripQuestion`, and the share step already renames audio to `audio-n.ext` and strips tags (the wav the voice makes has only `fmt` and `data` chunks). `test/voice.test.ts` checks the served page has none of it.

- **Engine:** [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) (`sherpa-onnx-node`, Apache-2.0), an `optionalDependencies` entry, so `npm install` on test and prod fetches the right native build and a box that can't just has the feature say "unsupported" rather than failing to start. It runs off the event loop (`generateAsync`), one request at a time, and the model is let go after 10 idle minutes.
- **Model:** Kokoro v1.0 in sherpa-onnx's int8 build (`kokoro-int8-multi-lang-v1_0`, Apache-2.0, 132 MB to download, 142 MB on disk). Eight British voices (the model has no Australian one). It is **not in git**. The first time anyone presses **Set up the voice** the server downloads the archive from the sherpa-onnx github release, checks it against the sha256 pinned in `voice.js`, unpacks only the files the English voices use with `tar` (so `tar` and `bzip2` have to be installed) and moves them into `storage/_voice/kokoro-int8-multi-lang-v1_0/`. A box with no route to github either sets `INTERACTIVES_VOICE_URL` to a mirror of that file, or unpacks `model.int8.onnx`, `voices.bin`, `tokens.txt`, `lexicon-gb-en.txt` and `LICENSE` into a folder and sets `INTERACTIVES_VOICE_DIR` to it (it then never downloads).
- **Words it doesn't know:** the engine has no spelling-to-sound rules of its own, only a 190,000 word British lexicon, so a word outside it (a name, a new term) is refused with `unknown-word` before anything is made, and the author types a *Say it like*. That is checked first on purpose: otherwise the engine silently skips the word.
- **Practice mode:** `Question.voice.device`. The Play node becomes a Read aloud node holding the word, and `serverMarkingProblem` refuses server marking for the question, so the share step marks it in the page and no grade is sent. Never offered as the way to a graded test.
- **Own audio:** `Question.voice.own` with `voice.ownAsset`. The Word audio choice in the Voice section picks between the made file (`voice.asset`) and the author's own (upload, Assets or a microphone recording, `src/lib/record-audio.ts`); both go in the same Play sound node, neither is deleted by switching, and Make the audio for all words skips own-audio questions (`voiceWordsIn`). `stripQuestion` drops `voice` as before.
- **Spell checkers and writing tools:** `Question.guard` (`mode` block, warn or off; `spellcheck`, `paste`, `exempt` as a SHA-256 hex of the teacher's code) is not secret, so it is served with the stripped question. The player carries the whole guard (`spelling-guard.ts`, marker data in `guard-tools.ts`), so the share page, the StudyDesk embed and single-file exports all have it. It sends `op: 'guard'` to the learner page, which posts it to `/learn/:token/guard`. The honest limits (OS and phone autocorrect, iOS treating autocorrect off as a hint, second devices, tools that inject nothing, markers that are guesses for Microsoft Editor, ProWritingAid, QuillBot and Ginger) are in the help topic Spelling tests and the section's own text.
- **Not done:** an Australian voice, American voices (they need the American lexicon loaded as a second engine), voices in other languages.

## Analytics: editor usage, published projects, errors

The editor records how it is used and where it breaks, and published projects report how they ran. It is mandatory (no setting), written down for users in the help topic "What the editor records" (`src/help/topics.ts`, id `what-is-recorded`), and goes the way every toolbox app's analytics do: si-manager's `utilities.js` `reportAnalytics` -> `si-analytics` `/analytics/ingest-bulk` -> `lti-analytics.ingest` (slimmed by `suite-libs/ingest-lean.js`). The editor page already loads `/utilities.js`; `src/lib/analytics.ts` sets the global `m` it reads (`m.user` from `fetchActivity`) and holds rows until the person is known (4 s at most).

**Editor rows** (`app: 'Interactives Editor'`, `src/lib/analytics.ts`, `usage.ts`):
- `feature` is the area: `session` (`start`, `active` = time with the tab showing and used, `end`), `project` (`open`, `close`, `create`, `list`...), `tool` (`use`, `time`), `panel` (`open`, `close`, `time`; the bottom tabs and `left-layers/assets/libraries`), `inspector` (`change`, by property name and `detail.node` layer type, once per drag), `node` (`add`, `first-add`), `doc` (`edit`, `duplicate`, `align`, `delete`...), `history` (`undo`, `redo`), `import` (`ok`, `failed`, `read`, `asset`), `export` (`download`), `help` (`topic`, `page`, `search`, `search-pick`), `preview` (`open`, `loaded`, `play`), `live` (`status`, `fallback`, `peer-joined`), `feature` (questions, steps, captions, variants, interface, libraries, a11y fixes, sharing; the action is the feature: `question-add`, `steps-enable`, `a11y-fix`...), `api` (`call`, `rejected`: server routes with ids taken out), `error`, `meta` (`dropped`).
- `featureID` is the action. `meta.ev` is `{thing, project, n, ms, detail, sum, t0, t1}`: what it was done to (a tool, property, layer kind, file type), the project id, how many times and how long over the window, low-cardinality facts, and numbers that add up. `meta.sid` is one id per tab visit, `meta.build` the editor build, `meta.v` the player version.
- Nothing is sent per event. Events are added up by (area, action, thing, project, detail) and one row per bucket goes out every minute and when the tab is hidden or closed (a beacon). A visit sends at most 2500 rows, 150 per flush, 300 buckets are held; the rest is counted in one `meta/dropped` row. `data-track="name"` on a button counts a click as `feature/name`.
- Never recorded: anything typed, any name (project, layer, variable, file, library), values, document contents, file names (only the extension). `thing` and detail values must be plain tokens (no spaces), numbers or booleans or they are dropped; the only free text anywhere is an error message, scrubbed.
- Faults are `feature: 'error'`, `featureID` the kind (`window`, `promise`, `boundary`, `api`, `chunk`, `import`, `export`, `save`, `live`, `open`, `project-script`, `project-shader`, `project-draw`...), `meta.err = {fp, kind, cls, msg, frame, where, detail, project, at}`. `fp` is a hash of the error class, the scrubbed message (quoted text, urls, ids, long numbers removed, 160 characters), the top stack frame without line, column or build hash, the kind and the place, so duplicates group across rebuilds. A fingerprint is sent in full 3 times per visit and at most 20 faults a minute; every occurrence is still counted in an `error` row with `meta.ev.n` and `detail.fp`. Sources: window `error`, `unhandledrejection`, `vite:preloadError` and caught lazy-chunk failures (`stale-build.ts`), the `ErrorBoundary` (its `name`, the first React component names), failed server calls (`db.ts`: 5xx and network failures are faults, 4xx are counted as `api/rejected`), importers and exports, save and live failures, and the preview's and canvas's script, shader and draw faults.

**Published project rows** (`app: 'Interactives Player'`): the player emits `diagnostic` events (`interactives-player/src/diagnostics.ts`: load time to first frame, frame/node/handler errors, scripts in the page or sandbox, script and shader layers, data sources, assets that would not load), exports forward them with `{source: 'interactives-diag'}` posts, and the learner page (`/play/:token`) checks each with `cleanDiag` (`shared/records.mjs`, embedded in the page) and sends `reportAnalytics('Interactives Player', <kind>, <project id>, {project, run, diag})` like learner records (feature is the kind, featureID the project id, so `idx_app_featureID_timestamp` serves per-project reads). They are sent whether or not anyone is signed in (nothing in one is about a person), at most 40 a page load. The plain `/s/<token>` page and a downloaded export have no analytics channel and send nothing. They are separate from learner activity (`app: 'Interactives'`, above), which a project can switch off.

**Reading it** (power users, `#/usage`, linked from the F9 banner on the projects page): `GET /api/analytics/usage?days=1|7|30|90|365` (`shared/usage-report.mjs`, counted in JS like Insights) gives a funnel (opened the editor, a project, added a layer, changed a property, preview, export or share), tools, panels, features, properties, layers, imports by format with failures, exports, help topics and searches that found nothing, server calls, builds and browsers, editor faults grouped by fingerprint with counts, people, visits, builds and last seen, and the published side: page loads, first-frame percentiles, faults by fingerprint, versions, projects with the most faults. Power users only (403 otherwise). No new index: the queries start with `app` and use `app_1_feature_1` / `idx_app_featureID_timestamp`.

Example queries against `lti-analytics.ingest` (mongosh):

```js
const since = Date.now() - 30 * 864e5
// which tools people use, and for how long
db.ingest.aggregate([{$match: {app: 'Interactives Editor', feature: 'tool', timestamp: {$gte: since}}},
  {$group: {_id: {a: '$featureID', t: '$meta.ev.thing'}, n: {$sum: '$meta.ev.n'}, ms: {$sum: '$meta.ev.ms'}, people: {$addToSet: '$meta.user.username'}}},
  {$project: {n: 1, ms: 1, people: {$size: '$people'}}}, {$sort: {n: -1}}])
// properties changed, by layer type
db.ingest.aggregate([{$match: {app: 'Interactives Editor', feature: 'inspector', timestamp: {$gte: since}}},
  {$group: {_id: {p: '$meta.ev.thing', node: '$meta.ev.detail.node'}, n: {$sum: '$meta.ev.n'}}}, {$sort: {n: -1}}])
// imports by format: worked, failed
db.ingest.aggregate([{$match: {app: 'Interactives Editor', feature: 'import', featureID: {$in: ['ok', 'failed']}}},
  {$group: {_id: {f: '$meta.ev.thing', r: '$featureID'}, n: {$sum: '$meta.ev.n'}}}])
// editor faults grouped by fingerprint, newest first
db.ingest.aggregate([{$match: {app: 'Interactives Editor', feature: 'error', 'meta.err': {$exists: true}}},
  {$group: {_id: '$meta.err.fp', kind: {$first: '$meta.err.kind'}, msg: {$first: '$meta.err.msg'}, where: {$first: '$meta.err.where'}, reports: {$sum: 1}, builds: {$addToSet: '$meta.build'}, last: {$max: '$timestamp'}}}, {$sort: {last: -1}}])
// the true count of one fault (including those held back from being sent in full)
db.ingest.aggregate([{$match: {app: 'Interactives Editor', feature: 'error', 'meta.ev.detail.fp': '<fp>'}}, {$group: {_id: null, n: {$sum: '$meta.ev.n'}}}])
// published projects: first-frame time by project, and script faults
db.ingest.aggregate([{$match: {app: 'Interactives Player', feature: 'load'}}, {$group: {_id: '$featureID', loads: {$sum: 1}, avgMs: {$avg: '$meta.diag.ms'}}}])
db.ingest.find({app: 'Interactives Player', feature: {$in: ['script', 'shader', 'draw', 'data', 'asset', 'error']}}).sort({timestamp: -1})
// one person's visits
db.ingest.find({app: 'Interactives Editor', 'meta.user.username': '<username>', featureID: {$in: ['start', 'end']}})
```

## MCP server (`mcp/`)

`mcp/server.ts` is an MCP server (JSON-RPC, no dependencies) that lets an AI agent join a project's live room as `<name> (AI)`, read it, edit it through the same ops as the editor, and see each person's selection. `npm run build:mcp` (also part of `npm run build`) bundles it with the player's catalog and the help topics into `mcp/dist/interactives-mcp.mjs`, which is committed like `dist/`.

Agents connect over the network: `index.js` serves the bundle at **`/interactives/mcp`** (MCP streamable HTTP, JSON replies only; `GET` is 405, `DELETE` with `Mcp-Session-Id` ends a connection). Each connection gets its own context (`runAs` + `AsyncLocalStorage` in `server.ts`): the caller's `X-Session-ID` (or `Authorization: Bearer <id>`), the name from `?agent=` (or `X-Agent-Name`), and its own live rooms. Tool calls go back into this server's api over loopback (`127.0.0.1:<port>`) with that session id, so an agent can do exactly what the session can. Connections idle for 2 hours are closed (rooms left), at most 200 are kept (the quietest goes first), and a request with an `Origin` from another host gets 403. The help page "AI agents (MCP)" builds the exact `claude mcp add --transport http ...` command and JSON config for the server it's opened on, with the reader's own session id filled in.

The same bundle still runs over stdio from a checkout (`node mcp/dist/interactives-mcp.mjs`, env `INTERACTIVES_URL`, `INTERACTIVES_SESSION_ID`, `INTERACTIVES_AGENT_NAME`), which the tests and local debugging use. `INTERACTIVES_MCP_NO_STDIO=1` stops the stdio loop; `index.js` sets it before importing the bundle. The live stream takes `?agent=<name>` for the agent's presence.

## Media bridge (microphone, camera, photos)

The share frame (`/s/<token>`) is sandboxed with an opaque origin, so the browser refuses it a microphone or camera even with `allow=` (checked in Chromium and Firefox). The devices belong to the **learner page** (`/play/<token>`) instead, which is trusted, and the project asks it by postMessage. The whole contract (declaration, states, wire, caps, what each side holds to) is in the player's README, "Microphone, camera and photos". What the server does:

- **The declaration is the server's copy.** `project.settings.sensors` (`microphone`, `listen`, `listenOnly`, `camera`, `photos`, `purpose`, `maxSeconds`, `noAlternative`) is read out of the page when the owner updates the share link (`declaredSensors` in `index.js`, using the bundle's `cleanSensors`) and kept on the share record as `share.sensors`, with the previous page's beside `share.previous` so a revert brings back the right one. `/play/<token>` builds its consent screen and limits from that, never from what the project says over the wire, so a project cannot ask for more than it declared when it was shared. A link shared before a project declared anything has none, and a project on it gets "not here" for every request.
- **The learner page, only for a link with a declaration**, gets the project's frame at `/s/<token>#ixm=<nonce>` (a fresh 16 byte nonce per page load, kept apart from the CSP nonce) and a module script that starts the bridge with that nonce and the declaration (written as script-safe JSON, since `purpose` is free text). A link with no declaration gets the page it always had: no nonce in the address, no module, no bridge.
- **CSP.** The only change to the learner page's policy is `media-src blob:`, so a recorded video can play from memory. The bridge file is `script-src 'self'`, and nothing else is opened: no `connect-src`, `img-src` or `frame-src` change, no `allow-same-origin`, no `allow-downloads` on the sandbox (downloads are made by the page itself, after a tap).
- **The iframe attribute.** The StudyDesk page that holds the learner page's iframe needs `allow="microphone; camera"`. Without it the page tells the learner in plain words that the course page does not allow it, using `document.permissionsPolicy`. For a toolbox item that builds that iframe, add `allow` to the code string and to its `updateInPlace.attributes` so an edit keeps it. Whether Moodle and TinyMCE keep the attribute on save is a separate check on test.
- **What is stored.** Nothing from a recording. Audio, video and photos live in the learner page's memory and the project's; nothing is sent to this server or the analytics, and the learner page's records and diagnostics never carry them. The learner's "Do not use my microphone or camera" is one boolean in the learner page's own `localStorage` (`ix-sensors-off`).
- **Reports with pictures.** A saved file can be a web page (`.html`, up to 16 MB, the rest 2 MB). The player replaces `[[image:<asset id or name>]]` in it with the picture as a `data:` address before it goes over the wire, and the bridge (`lockHtml` in the player's `protocol.ts`) puts a Content-Security-Policy meta first in its head (no script, no network, `data:` images only), so the page cannot run anything when opened. The branded Photo prompts notebook (`src/lib/branded/sets/media/photo-notebook.ts`) builds its hand-in report this way. `shared/media-bridge.mjs` is built (`npm run build:media`) and committed; rebuild it after any change under the player's `src/media/`.
- **The editor.** Project > Microphone and camera (`src/panels/SensorsSection.tsx`) edits the declaration and shows the consent screen as learners see it; the Preview has a pretend microphone and camera (`FakeMediaHost`, with a menu to make it fail); the accessibility checker's `sensors` rule (`src/lib/a11y/checks.ts`, `sensorRoutes`) wants a click, key or typed way to finish that does not go through the sensor, or a reason in `noAlternative`; the help topic is `sensors`.
- **Starters that use it.** The branded practice set: Shadow the model declares the microphone (one recording name, `take`, dropped on the next card, with a plain listen-and-repeat version for anyone whose microphone is not ready), and the Difficult conversation and Timed talk rehearsals carry an optional record-and-replay step that is off as shipped (their layers show only while `microphone == "ready"`, so ticking Microphone in the project turns it on). The shared wiring is `src/lib/branded/sets/practice/recording.ts`: Record is one Start recording node set to Start or stop (it quiets every sound first, and its Recorded output says so), and a button that plays a take back says Stop while it plays.
- **Live listening (version 2 of the wire).** `listen` in the declaration lets a project listen live: the learner page measures the microphone and posts a level and eight band numbers about 25 times a second, nothing is recorded, and the same consent screen, tap and bar (labelled Listening, with a Stop) apply. `listenOnly` also makes the page refuse every recording. Nothing about it is stored or sent to this server: the numbers go only from the learner page to the project's frame. The bridge file the page loads is still `shared/media-bridge.mjs`, rebuilt by `npm run build:media` whenever the player's `src/media` changes (the test in `test/server-media.test.ts` fails if it is stale), and a page built before version 2 is still answered for the requests it knew. The **Live sound lab** starter (`src/lib/branded/sets/media/live-sound-lab.ts`, tests in `test/branded-live-sound.test.ts`) is the pattern: displays read `listening ? micLevel : simLevel`, and a slider is the no microphone route.

## Standing rule: keep the docs current

**Any change that adds, removes or changes something a user would encounter updates the help (`src/help`: topics, search keywords, tutorials) in the same change**, including its screenshots and recordings whenever what's on screen or how it behaves changes.

Interactives is part of the StudyDesk Toolbox suite's two documentation sites, both served by si-manager:

- **`/toolbox-docs`**, for all staff, covers what Interactives is and how to get to it.
- **`/suite-docs`**, for admins only, covers how it's built, deployed and run: its server, storage, analytics and env vars.

A change to any of those updates those pages too. Neither site ever holds a credential.

## First load

The first download is what `src/main.tsx` reaches through static imports, and a test (`test/first-load-graph.test.ts`) fails when a file adds one of the big late-needed things back: help topics, starter sets, CodeMirror, React Flow or the player's source string. Those are chunks of their own, made with `lazyModule` (`lib/lazy-module.ts`): `ensure()` loads and awaits, `get()` is the module once it is in, `use()` is the hook (null while loading; `use(false)` only watches). They are `help/lazy.ts` (help screens, topics, search), `lib/branded-lazy.ts` (the starters), `components/CodeEditor.tsx` (CodeMirror, with a read-only copy of the text in its place) and `components/Dock.tsx` (`logicGraph`, the Interactions panel), plus the player string in `lib/player-source.ts`. A test that looks at what one of them draws awaits it first (`test/lazy-chunks.ts`).

`lib/warm.ts` fetches the likely ones quietly, one at a time while the browser is idle, a second after a project is on screen (not on Data Saver or 2G). Hovering or focusing Preview, Share or Export, or a help "?", starts its chunk straight away.

`index.html` does two more things before any bundle code runs. It paints `Shell` (the editor's frames, plain html, the same markup as `components/Shell.tsx`; `test/shell.test.tsx` keeps them equal) with the saved theme already on `<html>`, and when a session is already in hand (`?sessionID=` or this tab's sessionStorage) it starts `api/prefs` and, at `#/p/<id>`, `api/projects/<id>`, with the same `X-Session-ID` header `installSessionHeader` adds. The promises wait in `window.__ixEarly` and `lib/early-fetch.ts` hands each to `lib/prefs.ts` and `lib/db.ts` once: only for the same session, only while under a minute old, and a failed one is asked for again the ordinary way. Opened directly with no session the editor signs in first, so nothing starts early.
